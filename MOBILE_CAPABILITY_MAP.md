## Terms and classification

- **Conversation:** persistent interaction/transcript. Hermes primarily calls this a stored session; compression can rotate its stored ID through a lineage.
- **Run:** one agent execution. HTTP runs, desktop prompt executions, cron executions, and Kanban attempts have different identifiers and persistence.
- **Task:** durable work. Kanban cards and cron job definitions are durable task-like resources; an open chat is not automatically a task. A cron job's schedule is not itself a run.
- **Profile:** isolated Hermes configuration/state home, not proof of a running bot. A delegated subagent is not a persistent bot.

`Yes` means an implementation exists, not that this Studio has enabled/configured it. `Partial` identifies a narrower implementation than the intended feature. `No` means no first-class implementation was found in the audited source. `Direct` means the wire feature can be used without new Hermes functionality, subject to appropriate exposure/authentication. `Bridge` means normalization, aggregation, or exposure is needed. A missing core primitive stays missing; a bridge must not counterfeit it.

```json
{"jsonrpc":"2.0","id":"c1","result":{"session_id":"a1b2c3d4","stored_session_id":"<Hermes durable ID>","message_count":0,"messages":[],"info":{"model":"configured-model","cwd":"/Studio/project","lazy":true,"desktop_contract":2}}}
```

```json
{"jsonrpc":"2.0","id":"p1","result":{"status":"streaming"}}

{"jsonrpc":"2.0","method":"event","params":{"type":"tool.complete","session_id":"a1b2c3d4","payload":{"tool_id":"call_x","name":"read_file","args":{"path":"README.md"},"result":{"content":"…"},"duration_s":0.1}}}
```

```json
{"jsonrpc":"2.0","method":"event","params":{"type":"approval.request","session_id":"a1b2c3d4","payload":{"command":"<command>","description":"<reason>","pattern_key":"<key>","pattern_keys":["<key>"],"allow_permanent":false}}}
```

```json
{"jsonrpc":"2.0","id":"r1","method":"session.resume","params":{"session_id":"<Hermes durable ID>","profile":"default"}}
{"jsonrpc":"2.0","id":"r1","result":{"session_id":"a1b2c3d4","session_key":"<current Hermes durable ID>","messages":[],"running":true,"status":"working","inflight":{"user":"Inspect this project","assistant":"I found ","streaming":true},"info":{}}}
```

Resume rebinds the sole event transport of a live session. Two independent clients attaching to the same live agent can take the stream from each other. Stored IDs may rotate on compression; use the returned tip and preserve lineage.

### HTTP execution API (existing, but narrower)

```http
POST /v1/runs
Authorization: Bearer <API_SERVER_KEY>
Content-Type: application/json

{"input":"Continue the work","session_id":"api_conversation","conversation_history":[{"role":"user","content":"Earlier instruction"},{"role":"assistant","content":"Earlier answer"}]}
```

202: `{"run_id":"run_<uuid>","status":"started"}`. GET status returns `{"object":"hermes.run","run_id":"…","status":"running","session_id":"api_conversation","created_at":<epoch>,"updated_at":<epoch>,…}`.

GET events emits **data-only SSE**, with the event name inside JSON:

```text
data: {"event":"message.delta","run_id":"run_<uuid>","timestamp":123.0,"delta":"Working"}

data: {"event":"tool.started","run_id":"run_<uuid>","timestamp":123.1,"tool":"read_file","preview":"…"}

data: {"event":"run.completed","run_id":"run_<uuid>","timestamp":124.0,"output":"Done","usage":{"input_tokens":100,"output_tokens":20,"total_tokens":120}}

```

Other forwarded run events: `tool.completed` with `duration,error`; `reasoning.available` with `text`; `approval.request`, `approval.responded`, `run.failed` with `error`, `run.cancelled`. No run-start SSE event is enqueued here: initial start/state is HTTP status. `_thinking`/subagent progress are intentionally not forwarded. Events lack a replay cursor and ordinary tool events lack stable call IDs/full results.

Session chat stream is a different protocol: named SSE events `run.started`, `message.started`, `assistant.delta`, `assistant.completed`, `tool.started/completed/failed/progress`, `run.completed`, `error`, `done`. Payloads add `session_id,run_id,seq,ts`; this stream's generated run ID is **not registered** in `/v1/runs` for control. Its completion wrapper hardcodes success flags, so do not use it as authoritative failure classification without checking results/history. Chat Completions uses OpenAI chunks/`[DONE]`; Responses uses typed response events and function-call output items. Do not mix their decoders.

## Reliability and security findings that constrain implementation

1. **AS run streaming cannot resume:** `_handle_run_events` consumes a single shared `asyncio.Queue`; two consumers split events. Its `finally` removes the stream on disconnect. There is no `Last-Event-ID` handler.
2. **AS sweep can lose long-run control:** every 60s the sweep removes stream/agent/task/approval handles older than300s from creation, without requiring completion or checking subscription. Terminal statuses retain 3600s and vanish on process restart. The sweep does not itself preempt the executor thread. Ten stream slots are the concurrency limit, not a durable Studio execution registry.
3. **AS input model/history contract is weaker than it looks:** body `model` labels output/status while `_create_agent` resolves server configuration; `/v1/runs` does not hydrate DB history from a session ID, nor preserve every tool-call field when coercing explicit history. Do not use client-built transcripts as the preferred continuity path.
4. **WS disconnect is not replay:** sessions without `close_on_disconnect` are detached to a drop sink; idle orphans may be reaped after 20s. Running sessions survive the idle-orphan condition, but detach loses live events. Resume recovers partial assistant text and final history, not all tool/approval events. `close_on_disconnect:true` opts into immediate teardown.
5. **Approval continuity is incomplete:** queue/callback state is process-local and FIFO. No durable request ID, pending-list RPC, resolve-if-current primitive, or expired event contract. Five-minute default timeout/policy autoapproval can act while the phone is away. A remembered prompt must not become authority to approve the next queue entry.
6. **Activity scopes differ:** dashboard/TUI, API-server runs, messaging agents, cron, Kanban workers, delegated agents, and terminal processes are different registries. `is_active` uses activity within 300s; an unended session is not a running execution. APIServerAdapter is not IPC to GatewayRunner's other agents.
7. **Profiles need explicit routing:** some REST endpoints are properly scoped, others (memory/logs) are launch-home scoped; some legacy RPC title/delete/history paths use the shared `_get_db`. Desktop already uses separate backends per profile. Prefer that isolation instead of assuming `profile` fixes every handler in a pooled process.
8. **Remote auth is available, but broad:** public dashboard bind requires a provider; native clients can use cookies and fresh WS tickets. Internal `?internal=` is for Studio-spawned clients only. Dashboard tokens/admin APIs grant broad host access, including credential mutation/reveal and file operations. Tailscale ACLs and a mobile API allowlist are separate controls.
9. **Capability advertisements are not fully reliable:** AS reports `jobs_admin:false` while routes exist; docs and enabled-skill prose diverge from implementations. Probe read-only surfaces and report backend versions/effective flags rather than trusting marketing or booleans blindly.
10. **No global controls or APNs contract:** control of an unrelated messaging/cron/worker process cannot be added simply by reading its SQLite transcript. Hermes MCP permission responses are not real cross-process tool decisions. Native groups/Bot Mode/APNs remain absent.

## Implementation recommendation

**DIRECT:** structured desktop chat RPCs; stored session reads/CRUD with appropriate scope; raw streaming text/tool results; steer/cooperative stop for the owning RPC agent; profile/model/skills/tool/MCP summaries; cron and Kanban REST plus Kanban cursor events; host statistics and usage. Correct authentication/exposure is prerequisite, not currently certified.

**BRIDGE:** persistent Studio connection and fan-out; conversation/live-handle/run identity normalization; observed run journal/replay; Home aggregation with coverage metadata; scoped profile routing; prompt inbox with conservative expiry; safe artifact handles; sanitized settings/memory/log views; restricted mobile authentication. Reuse existing services, persistence, agent objects, scheduler and board operations.
