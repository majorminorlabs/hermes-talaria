# Bridge → Hermes source mapping

Baseline: installed checkout ~/.hermes/hermes-agent, HEAD 2a4c9afd7bd7b56d3e1f95524ca8956092f2904c. Hermes is an upstream dependency. This implementation changes no Hermes source, provider runtime, agent loop, scheduler, tool policy, profile files or production databases.

See [MOBILE_CAPABILITY_MAP.md](MOBILE_CAPABILITY_MAP.md) and [MOBILE_ARCHITECTURE.md](MOBILE_ARCHITECTURE.md) for the completed source audit. The actual implemented contract is [BRIDGE_API.md](BRIDGE_API.md).

## Why the HTTP run API is not used

gateway/platforms/api_server.py implements /v1/runs, but its shared queue can be consumed/destructively cleaned up by stream disconnects. A sweeper removes execution/stream/control state about 300 seconds after creation, including active work. Native run status also has process-local retention and different history/model behavior. Using it would make a reconnecting phone unreliable.

The bridge selects the existing desktop RPC agent path instead. It therefore does not need to keep an HTTP run handle alive, drain destructive queues or defeat a timer. Its own run observation survives indefinitely; bounded event retention is independent of run age. Both simulated >300-second observations and upstream handle loss are tested. This is not a patch or replacement runtime.

## Remaining limits

- One Hermes live session has one transport owner. A desktop resume/activate can steal the bridge's event sink without an observable ownership token. The bridge rejects known foreign handles but cannot reliably detect same-handle transport theft. Exclusive backend use is an operational requirement; supported shared observation requires an upstream primitive.
- Independent gateway/CLI/cron/worker processes do not all share a live-control registry. Readable transcripts and task records do not imply a control handle. Home/activity explicitly reports coverage.
- Exact dangerous approvals require current approval server requests. Legacy FIFO events remain unavailable remotely; stopping the entire owned run is a separate action. No secret, notification, or lock-screen approval controls are enabled.
- Unobserved outcomes are unknown. A backend restart can lose active execution/events; canonical text can recover persisted conversation content, not missing tool/approval events.
- Existing cron scheduling/dispatch and Kanban state transitions must remain healthy. The bridge does not silently start another scheduler or dispatcher. Kanban's non-CAS dashboard transitions can race independent clients; source guard failures surface as conflicts, and compound writes may be partial.
- Some tool progress is configuration-gated. Attachment discovery supports known structured paths, not every tool/provider/output convention. PDF conversion and some host metrics depend on upstream installed utilities.
- Model capabilities/configured providers are metadata, not a successful paid-provider test. This implementation's real execution tests use a local mock model, never production API keys.
- No Bot Mode registry, bot room/group orchestration, @bot mention routing, notification delivery, arbitrary settings, logs, unrestricted files or billing operations have been fabricated.

The bridge itself adds only durable observations, command receipts, auth, reconnect/replay, projections and narrow normalization. Conversations, executions, cron routines, Kanban tasks/attempts, tools, memory, skills and provider state remain Hermes-owned.
